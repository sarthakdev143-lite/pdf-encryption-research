### F-2026-001 - Encrypted PDF with object streams is not refused as password-protected; MuPDF parses unauthenticated ciphertext and reports 0 pages

- Status: **confirmed** - report drafted at `findings/reports/mupdf-encrypted-objstm.md` (not yet sent upstream)
- Severity (self-assessed): Low (no content disclosure; consistency/robustness bug)
- Affected: PyMuPDF 1.27.2.2 (bundled MuPDF) on Windows; engine behavior is
  MuPDF-core level, so mupdf-tools viewers (e.g. SumatraPDF) are plausibly affected
  too - verify before claiming.
- Bug class: encryption-handling divergence (unauthenticated parse path)
- Reproduction:
  1. `python generate_corpus.py` -> `corpus/base/rc4_40_r2__objstm.pdf`
     (or use the frozen PoC below; any encrypted PDF that uses object streams
     triggers it, all revisions R2..R6 tested)
  2. In Python:
     ```python
     import pymupdf
     d = pymupdf.open("corpus/base/rc4_40_r2__objstm.pdf")
     print(d.needs_pass, d.is_encrypted, d.page_count)  # 1 True 0
     d[0]  # IndexError: page 0 not in document  (NOT a password error)
     ```
  3. stderr shows `MuPDF error: library error: zlib error: incorrect header check`
     and `MuPDF error: format error: corrupt object stream (2 0 R)` - MuPDF is
     decoding encrypted object-stream bytes as if they were plaintext.
- Minimal PoC file: `findings/poc/F-2026-001-encrypted-objstm-no-password-error.pdf`
  (synthetic, generated by this repo; password is `Us3r-Passw0rd!`)
- Control: `findings/poc/F-2026-001-control-encrypted-plain-refuses.pdf` (same
  content, no object streams) correctly raises
  `ValueError: document closed or encrypted` on page access.
- Expected behavior (per ISO 32000-2 §7.6): an encrypted document whose user
  password is not supplied must be refused uniformly. The non-object-stream path
  already behaves this way. MuPDF does report `needs_pass=True`, but any caller
  that goes by page count, iteration, or exception type sees an apparently empty
  valid document instead of "password required".
- Actual behavior: `page_count=0`, page access raises `IndexError`, engine emits
  zlib/object-stream corruption errors from unauthenticated ciphertext. With the
  correct password the same file yields 2 pages of text (file is valid).
- Impact: silent data loss / wrong error surface in MuPDF-based viewers and
  pipelines; unauthenticated parse of ciphertext (robustness). NO content
  disclosure observed - extracted text is empty on every engine.
- Cross-engine comparison (this repo's triage, 210 files x 5 engines):
  pypdf, pdfminer.six, pypdfium2 and pikepdf/qpdf all refuse these files with
  password/decryption errors. MuPDF is the only outlier.
- Disclosure: not yet reported. Planned: MuPDF bug tracker (Artifex), cc
  PyMuPDF if the wrapper surface matters. Ask 90-day window before publishing.
  Re-verified 2026-10-29 on PyMuPDF 2.0 / MuPDF 1.28.5 (VPS): behavior
  unchanged; see `findings/reports/mupdf-encrypted-objstm.md` §Disclosure.
- Notes: harness lesson - PyMuPDF prints native engine diagnostics to **stdout**,
  which silently corrupts JSON subprocess protocols (see `capture_fd1` in
  `triage.py`).

### F-2026-002 - reportlab AES-256 writes non-conforming /UE, /OE, /Perms; files fail in MuPDF, pypdf, pdfminer with the correct password

- Status: **confirmed + fix validated** - report drafted at
  `findings/reports/reportlab-aes256.md` (not yet sent upstream)
- Severity (self-assessed): Medium (interoperability; no confidentiality impact)
- Affected: reportlab 5.1.0, `StandardEncryption(strength=256)` (AES-256, R5)
- Bug class: writer-side encryption conformance bug
- Reproduction: `python writers.py` -> `corpus/writers/reportlab_s256.pdf`;
  see the report for the 15-line generator. Password: `Us3r-Passw0rd!`
- Minimal PoC: `findings/poc/reportlab_s256_nonconforming.pdf`;
  fixed output: `findings/poc/reportlab_s256_fixed.pdf`
- Expected (ISO 32000-2): `/UE` 32 bytes, `/OE` 32 bytes, `/Perms` 16 bytes,
  AES-256-CBC with no padding for the file key.
- Actual: 48 / 48 / 32 bytes - a PKCS#7 padding block is added because
  `pdfencrypt.py` finalizes the pyaes encrypter with `encrypter.feed()`.
- Impact: correct password cannot open the file in MuPDF 1.27.2
  (`FileDataError`), pypdf 6.20.0 and pdfminer.six 20260107
  (`Invalid key size (384) for AES`). qpdf/pikepdf 10.17, PDFium 5.13 and
  pdf.js tolerate the padding.
- Fix: construct the three encrypters with `padding=pyaes.PADDING_NONE`.
  Validated end-to-end: sizes become 32/32/16 and both MuPDF and pypdf open the
  file and extract the canary. Script: `findings/poc/validate_reportlab_fix.py`.
- Disclosure: reportlab maintainers (tracker / GitHub mirror), 90-day window,
  offer the patch as a PR. Re-verified 2026-10-29 (static field sizes on frozen
  PoC unchanged); see `findings/reports/reportlab-aes256.md` §Disclosure.
- Notes: no content leak - all readers still refuse without the password.

## Observations (not reportable as-is)

### O-2026-001 - /Encrypt inheritance across incremental updates diverges between readers

- Experiment: `python incremental.py` (report: `findings/incremental.md`)
- Setup: encrypted seed + appended revision (new Catalog/Pages/Page/Contents in
  plaintext, new xref, trailer **without /Encrypt**, `/Prev` -> original xref).
- Result without a password:
  - pypdf, PDFium: still treat the document as encrypted and refuse
    (`FileNotDecryptedError`, `Incorrect password error`).
  - MuPDF, pdfminer.six, qpdf/pikepdf, pdf.js: treat the newest trailer as
    authoritative, open the file and render the appended plaintext page.
  - Original encrypted page content was never extracted by any engine (0/24).
- Interpretation: a locked PDF can be given a new, unencrypted first revision
  without knowing the password on 4 of 6 stacks. This is an integrity property
  of the format (no MAC/signature over revisions), not a break of
  user-password confidentiality. It is the structural basis for PDFex-style
  attacks, which additionally need a viewer that later decrypts with the
  victim's password. Not filed upstream; document in the write-up.
