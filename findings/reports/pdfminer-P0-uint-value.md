# pdfminer.six: `/P 0` in the encryption dictionary raises `struct.error` instead of a pdfminer exception (and the file is unopenable even with the correct password)

**Project:** pdfminer.six
**Version:** 20260107 (Python 3.14, Linux; file layout identical on all platforms — pure-Python bug)
**Severity:** Low (robustness / interoperability; no confidentiality impact — no content is disclosed)
**Status:** drafted, not yet sent upstream (90-day window starts on report)

## Summary

When a PDF's document encryption dictionary carries `/P 0`, pdfminer.six fails
with `struct.error: 'L' format requires 0 <= number <= 4294967295` — an
exception type outside pdfminer.six's own hierarchy — instead of either raising
`PDFPasswordIncorrect` (no/wrong password) or opening the file (correct
password). The file is therefore unopenable in pdfminer.six **even with the
correct user password**, while five independent engines (pypdf, MuPDF,
PDFium, qpdf, pdf.js) parse the same dictionary and proceed to normal
password authentication.

`/P` is a signed 32-bit permissions integer (ISO 32000-2 §7.6.3.3); `0`
(grant nothing) is a legal value. Five of the six engines tested accept it
without remark; only pdfminer.six converts it to an out-of-range unsigned
value before key computation.

## Reproduction (synthetic files only, passwords `Us3r-Passw0rd!` / `0wner-Passw0rd!`)

Minimal PoC (frozen, generated by this repo — a same-length `/P` patch of a
repo seed, so no real document is involved):

- `findings/poc/O-2026-006-pdfminer-P0-min.pdf` — triggers with and without password
- `findings/poc/O-2026-006-pdfminer-P0-appended-aes.pdf` — appended-revision variant (AES-256 seed)

```python
from pdfminer.pdfdocument import PDFDocument
from pdfminer.pdfparser import PDFParser

with open("findings/poc/O-2026-006-pdfminer-P0-min.pdf", "rb") as f:
    PDFDocument(PDFParser(f), password="Us3r-Passw0rd!")  # correct password
# struct.error: 'L' format requires 0 <= number <= 4294967295
```

The same `struct.error` is raised with an empty password. A control file
identical except for `/P 1` opens the auth path normally (`PDFPasswordIncorrect`
without password).

## Cross-engine comparison (PoC, no password)

| Engine | Version | Result on `/P 0` file |
|---|---|---|
| pdfminer.six | 20260107 | `struct.error` (uncaught-class outlier) |
| pypdf | 6.21.4 | `FileNotDecryptedError` (clean refuse) |
| PyMuPDF (MuPDF 1.28.5) | 2.0 | `ValueError: document closed or encrypted` (clean refuse) |
| pypdfium2 (PDFium) | 5.14.0 | `Incorrect password error` (clean refuse) |
| pikepdf (qpdf 10.17.0) | 10.17.0 | `PasswordError: invalid password` (clean refuse) |
| pdf.js | 6.4.299 | `PasswordException: No password given` (clean refuse) |

No engine discloses original page content (12/12 no-password probes across
both PoCs: 0 leaks). `/P` values `-4` (baseline), `1`, and `2147483647`
(max int32) all behave identically clean on all six stacks — only exactly
`0` trips the outlier.

## Root cause

`pdfminer/pdftypes.py`, `uint_value` (verified at 20260107):

```python
def uint_value(x: object, n_bits: int) -> int:
    """Resolve number and interpret it as a two's-complement unsigned number"""
    xi = int_value(x)
    if xi > 0:      # <-- off-by-one: 0 must take the pass-through branch
        return xi
    else:
        return xi + cast(int, 2**n_bits)
```

`/P 0` falls into the `else` branch and yields `0 + 2**32 = 4294967296`,
which `struct.pack("<L", self.p)` in
`PDFStandardSecurityHandler.compute_encryption_key` (`pdfdocument.py`)
rejects with `struct.error`. `struct.error` is not a subclass of
`PDFException`, so callers catching only pdfminer exceptions (e.g. data
pipelines catching `PDFPasswordIncorrect` / `PDFEncryptionError`) see an
unexpected exception class — effectively a robustness/DoS wart on any
untrusted-PDF path, and an interop failure for conforming files that use
`/P 0`.

## Suggested fix (one line, validated in isolation)

```python
    if xi >= 0:
        return xi
```

Simulation of current vs fixed `uint_value` + `struct.pack("<L")` for
`/P` in `{-4, 0, 1, 2147483647}`: only `0` overflows today (`4294967296`);
with `>=`, `0` packs cleanly and `-4`/`1`/max-int32 results are
byte-identical. Offered as a PR on request.

## Impact

- No user-password content disclosed (0/12 probes). Not a confidentiality bug.
- A conforming encrypted file with `/P 0` cannot be opened in pdfminer.six
  with any password; unexpected `struct.error` class can escape
  `except PDFException` handlers in downstream tools (pdfplumber, data
  pipelines).
- Fix is a one-character-class change with no behavioural effect on any
  other `/P` value.
